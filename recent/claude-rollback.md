### What this table actually shows

The genuinely hard 30% of Gearset's rollback — items **1, 3, and 9** — all stem from one design decision: comparing against *live org state*, not git history. That's what lets them roll back a change even if someone made unrelated clicks in Production afterward, and it's what makes their engine expensive to rebuild (months, not weeks).

The Stack Exchange workaround sidesteps that decision entirely. It redefines "rollback" as **"redeploy the org to match a previous git commit"** rather than **"undo exactly this deployment regardless of what happened since."** For a team with strict git discipline (nothing ever deployed or clicked outside the pipeline), those two definitions converge and the cheap version is functionally equivalent — which is exactly why it's "far more straightforward": it's solving an easier problem, not a cheaper version of the same problem. The moment an admin makes an out-of-band change in Production, the two diverge, and only Gearset's org-state-aware version notices.

Good instinct — Profiles and Permission Sets are the one metadata family where the "redeploy the old file" trick from the Stack Exchange workaround can quietly fail without giving you any error at all. The root cause is that the Metadata API treats them as **merge/additive instructions**, not as a declarative full-state replacement — so "the old XML" and "the actual previous org state" are not the same thing.

| Problem | Why it happens | Effect on the git-delta rollback trick | How Gearset's approach mitigates it | DIY effort to handle properly |
|---|---|---|---|---|
| **Additive-only / sparse permission semantics** | Profile/PermissionSet sub-elements (field, object, tab, user, custom permissions) only list *enabled* grants — disabled permissions simply aren't included in the document; to turn one off you must explicitly include an element that disables it | If the bad deploy *granted* new access, the pre-deploy file version never mentions that grant at all (it didn't exist yet) — redeploying it changes nothing; the grant silently survives the "rollback" | Their comparison engine diffs against live org state and can emit an explicit revoke directive, not just redeploy a stale file | **Medium–High** — your inverse-package generator must diff old-vs-new field/object entries and emit explicit `false` blocks for anything newly granted, not just hand back the old file |
| **Monolithic single file per profile** | One `Profile.xml` bundles every permission type for that profile in one file; there's no per-permission decomposition | A file-level git revert reverts *everything* else that landed in that file since, including unrelated, legitimate changes from other workstreams — collateral damage | Gearset's UI lets you choose individual elements within the metadata or specific lines of XML to deploy and leave out in-progress changes | **High** — needs custom XML-element surgery (parse, isolate by node identity, patch), not something git or `sgd` does natively |
| **Order-dependency validation errors** | Salesforce validates intermediate permission states during deploy, not just the end state | A documented real case: removing Delete and Modify All permission from a Profile triggers a validation error "Manage Cases requires delete permission," requiring the removal to be split into two sequential deployments | Gearset documents the two-step workaround explicitly | **Medium** — needs hardcoded CRUD-hierarchy sequencing logic (Delete→Edit→Read ordering) or trial-and-error split deploys |
| **Incomplete retrieve = incomplete snapshot** | The subcomponents Salesforce returns for a profile depend on which other metadata types are included in the same retrieve filter — select only `Profile` and you get just user permissions, no FLS | If your "previous version" was captured with a narrow filter, it was never a true full state — the rollback baseline is wrong before you even start | Gearset maintains a documented reference table of which types must be bundled together for a complete profile retrieve | **Low–Medium** — mostly a configuration fix (always bundle Profile with the relevant CustomObject/Field/ApexClass types), not real engineering |
| **Standard-profile default pollution on new-profile creation** | Deploying an entirely new profile causes some object permissions to be falsely set to true, inherited from the Standard User profile defaults in the target org | If the "bad deploy" was a brand-new profile, live state has already diverged from *both* your old and new git versions before rollback even runs | Gearset documents a two-pass deploy (profile first, then a corrective pass for the missed permissions) | **Medium** — requires a deliberate two-pass script, plus awareness of the quirk |
| **Permissions the API can grant but never revoke** | Confirmed, hard platform limits: the API can add custom metadata type access to profiles but not remove it, can add existing custom permissions but not delete them, and can add or change record types but cannot delete them or their visibility | No deploy-based rollback — Gearset's or yours — can undo these. The "rollback" will run successfully and accomplish nothing for these specific grants | Problem Analyzer flags it and tells you to delete manually in Setup instead of wasting a deploy cycle on it | **Not solvable via API at all** — manual Setup-UI step, full stop, regardless of tooling |
| **Permission Set Group / Muting Permission Set interaction** | A PSG's effective access is the union of its member Permission Sets *minus* whatever an associated Muting Permission Set explicitly subtracts | Rolling back one member Permission Set without recalculating the muting layer can leave users with the wrong net-effective access — looks fixed, isn't | Not confirmed in public docs — likely partially covered by their general dependency checks, but I have no direct source for this one specifically | **High** — needs the PSG/muting relationship modeled explicitly; generic file-level tooling won't catch this at all |

### The underlying pattern

Every metadata type discussed earlier in this thread (Flows, layouts, queues) has *some* deterministic, mechanical fix because the API treats them as declarative — "this is the full state, replace it." Profiles and Permission Sets break that assumption: they're **patches applied on top of whatever's already there**, and patches don't have a clean inverse unless you explicitly compute one. That's the real reason this category is hard to roll back correctly — not a tooling gap, but a fundamental property of how Salesforce designed the API for this metadata family. It's also exactly the kind of nuance that justifies Gearset charging for a real comparison engine instead of "just redeploy the old file": the cheap workaround is right *most* of the time, until a deployment specifically grants permissions, at which point it fails silently rather than loudly — arguably the worst kind of failure to have in a rollback tool.

Yes — that's exactly the pragmatic compromise most teams without Gearset land on. You can't fully automate the revoke-semantics gap cheaply, but you *can* close most of the risk by pairing the cheap git-delta rollback with a documented permissions ledger and a few mandatory manual checkpoints. It converts an engineering problem into a governance/process one — which is a fair trade for many teams, with one caveat at the end worth being honest about.

| Stage | Manual artifact / action required | What it compensates for | Residual risk |
|---|---|---|---|
| **1. At PR/merge time** | PR must include an explicit "Access changes" section: for every Profile/PermissionSet touched — component, permission type, before-value, after-value | The additive-API gap — captures *intent* (including intended revokes) that a raw file diff won't show on its own | Entirely dependent on the developer/reviewer filling it out honestly and completely; nothing enforces accuracy |
| **2. At rollback decision time** | Before deploying the `sgd`-generated inverse package, a human (release manager) checks it against the Stage-1 ledger and manually adds explicit `<editable>false</editable>` / `<readable>false</readable>` blocks for anything the ledger marked as a new grant | The single biggest gap identified earlier: omission ≠ revoke, so the automated inverse package alone won't actually pull back newly-granted access | Manual XML editing under incident pressure is slow and error-prone — exactly when mistakes are costliest |
| **3. Sequencing check** | Reviewer checks the ledger for known CRUD-order dependencies (Delete→Edit→Read) and decides whether the rollback needs splitting into two sequential deploys | The order-dependency validation errors Salesforce throws when removing a permission whose dependent permission is still active | Relies on the reviewer actually knowing this Salesforce quirk — institutional-knowledge dependent, not codified |
| **4. Post-rollback verification** | After deploy, manually spot-check the affected Profile/PermissionSet in Setup (or a quick `sf data query` against `FieldPermissions`/`ObjectPermissions`) to confirm live state, not just "deployment succeeded" | "Deploy succeeded" ≠ "state is correct" — additive metadata can report success while leaving stale grants in place | Time-consuming, easy to skip under pressure, doesn't scale once a release touches many fields/objects |
| **5. Optional cheap automation assist** | A CI step (reusing the XML-canonicalization script from earlier) that posts a PR comment listing exactly which permission entries were added/removed in any changed Profile/PermissionSet file | Doesn't generate the rollback, but gives the human reviewer in Stages 1–2 a ready-made list instead of reading raw XML by eye | Still requires a human to act on the list — this narrows the manual-error surface, it doesn't remove it |

### The honest trade-off

This setup is genuinely viable and is, in practice, how a lot of mid-size Salesforce teams run permission changes safely without buying a tool like Gearset — a written access-change ledger is good security/audit hygiene anyway, independent of which rollback strategy you use. The cost isn't engineering hours, it's **discipline**: every Profile/PermissionSet change needs a human to stop, document, and double-check, every single time, including during an incident when people are most tempted to skip steps.

Where this stops scaling: high release frequency, multiple parallel teams touching the same profiles, or any setup without a dedicated release-manager role to own Stage 2–4 consistently. At that point the manual checkpoints either get skipped under pressure or become the new bottleneck — which is precisely the gap Gearset (and similar tools) are selling against: not "can a human do this," but "can a human reliably do this every time, fast, at 2am, without a dedicated process owner in the room."
